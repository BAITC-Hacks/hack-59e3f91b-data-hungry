# Семантический поиск по каталогу ЕКТ

Дата проверки: 23.09.2026. Источник: локальная выгрузка API ekt.kz, 15 035 товаров и детальных карточек. Для создания векторов использован OpenAI-совместимый endpoint `https://llm.nitec.kz/v1/embeddings`; реальные размерности проверены ответом API. Ключ вводился через скрытый запрос терминала и не сохранялся в проекте.

## Метод

Для выбора конфигурации использованы одни и те же 2000 товаров: 23 товара из контрольных запросов и 1977 случайно выбранных товаров с seed `42`. [23 контрольных запроса](../backend/tests/fixtures/semantic_queries.json) составлены как запросы покупателя к конкретным известным карточкам. Метрики: Hit@1, Hit@5 и MRR@10 по идентификатору товара. Для стратегии с несколькими фрагментами оценкой товара служит максимальное косинусное сходство его фрагментов. Векторы нормализуются перед поиском.

Сравнивались три стратегии:

1. **compact** — название, артикул, категория и ключевые характеристики; один вектор на товар.
2. **full** — то же, плюс до 480 символов описания и до 320 символов характеристик; текст ограничен 900 символами для совместимости с моделью E5 (лимит 512 токенов); один вектор на товар.
3. **split** — отдельный вектор для названия с характеристиками и перекрывающиеся фрагменты описания длиной до 620 символов с перекрытием 100; несколько векторов на товар.

Цена и остатки в векторы не включались: они меняются и должны запрашиваться из API ЕКТ при показе карточки. Для Qwen3 и E5 запросы снабжались одинаковой инструкцией на английском о поиске товаров; BGE-M3 получала исходный запрос. Это соответствует рекомендациям авторов [Qwen3](https://huggingface.co/Qwen/Qwen3-Embedding-8B), [E5](https://huggingface.co/intfloat/multilingual-e5-large-instruct) и [BGE-M3](https://huggingface.co/BAAI/bge-m3).

Для рабочего файла выбрана **multilingual-E5-large-instruct + full**: это лучший результат на полном каталоге по Hit@1 и MRR@10, при одинаковом с Qwen3 Hit@5 и примерно втрое меньшем размере. На 23 запросах её преимущество перед Qwen3 — всего один правильный первый результат; считать эту разницу надёжным доказательством превосходства модели нельзя. Выбор также учитывает размер и скорость поиска. Победа Qwen3 на выборке из 2000 товаров не сохранилась при добавлении всех конкурирующих карточек.

Итоговый файл: `backend/data/semantic_catalog.sqlite`; в нём 15 035 разных товаров и 15 035 нормализованных векторов по 1024 числа `float32`. `PRAGMA quick_check` вернул `ok`. Полные коллекции Qwen3 и BGE-M3 сохранены в исключённой из Git папке `backend/data/semantic_benchmark/` для повторной проверки. Пробный CLI-поиск по запросу о светильнике с датчиком движения вернул соответствующие модели.

Это небольшой тест на поиск конкретной карточки. Он не доказывает превосходство на всех формулировках, языках и задачах поиска аналогов. В контрольных запросах встречаются названия и характеристики целевых товаров, поэтому результаты могут быть выше, чем на реальных диалогах покупателей. Следующий шаг для надёжной оценки — собрать реальные обезличенные запросы и разметить все релевантные товары, а не один известный артикул.

## Гибридный поиск: эмбеддинги + FTS5

Текущий API поиска товаров и инструмент `search_products` агента объединяют по 100 кандидатов из векторного поиска и SQLite FTS5. Для товара из объединения рассчитывается

`score = 0,60 × cosine_norm + 0,15 × semantic_hit + 0,10 × fts_hit + 0,15 × bm25_norm`.

`semantic_hit` и `fts_hit` равны 1, если товар попал в соответствующую сотню результатов, иначе 0. Косинусное сходство нормализуется по диапазону векторной сотни, а [BM25 FTS5](https://www.sqlite.org/fts5.html#the_bm25_function) сначала меняет знак (меньшее исходное значение лучше), затем нормализуется по диапазону FTS-сотни. Значения вне диапазона обрезаются до 0–1. Компоненты видны в CLI `scripts/hybrid_search.py search`. Точный артикул остаётся первым независимо от коэффициентов. Цена и остаток в поисковом score не участвуют; карточки по-прежнему берут их из API ЕКТ.

Три фиксированных набора коэффициентов сравнили на тех же 23 запросах по всему каталогу. Это **исследовательская проверка**, а не независимый тест: набор запросов уже использовался при выборе модели, поэтому разница между профилями не доказывает обобщаемое преимущество.

| Поиск | Косинус / попадание в векторный поиск / попадание в FTS / BM25 | Hit@1 | Hit@5 | MRR@10 |
| --- | --- | ---: | ---: | ---: |
| Только E5 | — | 69,6% | 82,6% | 0,753 |
| Только FTS5 OR-кандидаты | — | 39,1% | 78,3% | 0,565 |
| Гибрид, акцент на эмбеддинги **(выбран)** | 0,60 / 0,15 / 0,10 / 0,15 | **69,6%** | **91,3%** | **0,783** |
| Гибрид, равномернее | 0,40 / 0,10 / 0,20 / 0,30 | 65,2% | 91,3% | 0,770 |
| Гибрид, акцент на FTS | 0,30 / 0,05 / 0,25 / 0,40 | 69,6% | 91,3% | 0,789 |

Профиль с сильным FTS дал MRR выше выбранного на 0,006 при одинаковых Hit@1 и Hit@5. Из-за малого набора запросов выбран профиль с большим весом эмбеддингов: FTS используется как дополнительное свидетельство, а не главный сигнал. У существующего поиска `catalog.search` другая, более точная лексическая сортировка: её ориентир 65,2% / 73,9% / 0,688 приведён выше; строка «Только FTS5 OR-кандидаты» относится именно к списку кандидатов гибридного поиска.

Если нет доступного embedding endpoint или файла коллекции, API и агент автоматически используют прежний локальный лексический поиск. Для работы гибрида на другом сервере нужно перенести оба локальных SQLite-файла (`catalog.sqlite` и `semantic_catalog.sqlite`) и настроить NITEC с ключом либо локальную модель через `EKT_EMBEDDING_BASE_URL`. Ключ в коллекции и отчёте не хранится.

## Один реранк после объединения

Отдельный реранк каждого источника заставил бы дважды обрабатывать часть одних и тех же товаров и не позволил бы модели сравнить FTS-кандидатов с векторными кандидатами напрямую. Поэтому один вызов `/v1/rerank` получает первые 30 товаров **после** объединения. Тексты для реранкера берутся из сохранённых в коллекции названий, описаний и характеристик. Реранкер меняет порядок только внутри этой тридцатки; точный артикул после этого всё равно ставится первым. При ошибке реранкера остаётся гибридный порядок, при ошибке эмбеддингов — локальный лексический поиск.

В доступном через NITEC списке моделей проверены `BAAI/bge-reranker-v2-m3` и `Qwen/Qwen3-Reranker-8B`; обе ответили через `/v1/rerank`. На тех же 23 запросах по 15 035 товарам получено:

| Финальный порядок | Hit@1 | Hit@5 | MRR@10 | Среднее время только вызова реранкера |
| --- | ---: | ---: | ---: | ---: |
| Гибрид без реранкера | 69,6% | 91,3% | 0,783 | — |
| Гибрид + BGE reranker v2 m3 | 73,9% | 95,7% | 0,841 | 317 мс |
| **Гибрид + Qwen3 Reranker 8B (выбран)** | **82,6%** | **100%** | **0,913** | **394 мс** |

Время измерено от отправки до получения ответа NITEC на 30 документов, без получения эмбеддинга, локального поиска и карточек ЕКТ. Это не гарантия задержки на другом сервере. В выбранной конфигурации дополнительное попадание в топ-5 получилось на 23 из 23 запросов; оценка на независимых реальных запросах ещё нужна. Настройки: `NITEC_RERANK_MODEL` меняет модель, `EKT_RERANK_ENABLED=0` отключает этап. Воспроизведение: `uv run --project backend python backend/scripts/hybrid_search.py evaluate --rerank`.

Скрипт [semantic_catalog.py](../backend/scripts/semantic_catalog.py) возобновляет построение после прерывания и предоставляет поиск из командной строки. Файлы коллекций и временные результаты исключены из Git; код, запросы и этот отчёт доступны для воспроизведения.
